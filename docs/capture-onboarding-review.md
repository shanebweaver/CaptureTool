# Capture onboarding and standalone Text Extraction

**Superseded behavior:** [Explicit analysis actions](capture-analysis-explicit-actions.md) replace automatic scanning, open-triggered analysis, automatic naming, and first-launch AI consent. The [unified text experience](unified-text-experience.md) now brings saved results and current-image extraction into the Text tab. The sections below describe earlier implementations.

The capture-analysis invitation appears the first time the main window is shown without analysis consent. Its aurora and spark artwork introduces practical text, recording and naming features. Allow grants analysis consent and defaults scanning and automatic names on, while preserving explicit opt-outs. Not now leaves scanning off and is remembered across restarts. The Details Text/Transcript tab can reopen this invitation, and its Enable capture analysis button remains available after dismissal. Settings and other shared-consent entry points use the same invitation.

The main window owns and serializes analysis, standalone OCR and telemetry consent dialogs. Hidden/closed startup windows cancel their invitation; a cancelled window lifetime is not recorded as a decision. Basic Details never opens a consent prompt. Restoring a remembered Text tab after capture or navigation also does not trigger a prompt automatically; selecting the tab or its enable button is an explicit entry. Dialogs follow the main window’s theme.

## Defaults and remembered choices

Granting shared consent enables the two configurable AI preferences, scanning and automatic capture naming, when no choice is saved. Scanning preference is separate from consent: revoking consent immediately stops work without turning that suspension into an explicit opt-out. A later grant honors a saved scanning-off choice. Naming defaults are applied atomically in the protected catalog, so a concurrent or earlier explicit naming-off choice wins; even turning an already-off option off records a choice. Restarts retain both preferences. Developer feature flags and standalone Text Extraction permission remain separate.

The history-analysis offer appears only when an available registered source or an eligible captured recent item exists. Missing files, relative paths and merely opened recent items do not trigger it. Declining leaves history unscheduled, and an empty library proceeds directly from consent to enabled defaults.

Policy schema 3 adds the scanning preference; catalog schema 5 adds the naming preference. Older saved off values cannot reliably distinguish an untouched default from an explicit choice. Migration conservatively preserves policy v2 and catalog v4 values. Earlier catalogs, which predate naming, can receive its new default. No migration grants consent, resets protected records, renames historical captures, or overwrites established names.

## Independent Text Extraction

The existing image-toolbar tool keeps the `ImageEdit_TextExtraction` feature flag, original Text Extraction consent dialog and original `Settings_AiConsent_TextExtraction` preference. It renders the current editor image, performs OCR and QR detection, and retains edit-revision/cancellation protection. It neither reads the analysis catalog nor grants scanning consent. The unused metadata-to-toolbar reader and its request payload have been removed. Other AI editing tools retain the capture-analysis consent owner; this change isolates Text Extraction specifically.

Capture-analysis consent cannot authorize the standalone tool, and revoking analysis cannot cancel its independent work. Settings includes a separate Text Extraction permission card using the original consent dialog. Declining keeps its checkbox off; revoking cancels active OCR immediately, including while its settings save is pending or fails. A newer revocation fences an older pending grant. Settings reflects toolbar consent changes, and existing explicit standalone grants remain valid. The control follows tool availability, while an existing grant remains visible for revocation.

## Startup errors

Unrequested storage/policy failures while capture analysis is disabled remain in service state without producing a background error toast, including when visiting Settings. Page refresh only observes state. Explicit analysis commands, save failures and errors during enabled analysis continue to report failures. Command notification eligibility ends with the command; failures already captured during it survive a delayed UI dispatch. This does not discard or repair existing protected data. The reported “Capture Memory storage is unavailable” toast exposed a page-refresh notification bug; its underlying persisted-data status is separate and has not been diagnosed.

The Settings regression reproduced four unwanted-notification cases before the fix. All 288 presentation tests pass afterward, including delayed command failures and enabled-analysis errors. An isolated native desktop test with an unreadable control file confirms repeated Settings visits stay quiet with scanning off, explicit enable reports the storage error, and neither path resets that file. The x64 native publish passed with only the four previously accepted vendor warnings. Results: `artifacts/settings-error-presentation.log`, `artifacts/settings-error-publish.log`, and `tests/CaptureTool.UiTests/TestResults/settings-error-native.trx`.
