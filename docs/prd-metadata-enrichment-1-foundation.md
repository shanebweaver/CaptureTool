# Metadata enrichment — slice 1: evidence and freshness

Status: implemented on `codex/capture-metadata-enrichment-foundation`, awaiting slice review. Parent feature branch: `codex/capture-analysis-core`. See the [foundation review](metadata-enrichment-foundation-review.md).

## Goal and delivery order

Turn existing capture metadata into useful, explainable insights without scanning the media again. Deliver in four reviewable slices:

1. [Evidence and freshness](prd-metadata-enrichment-1-foundation.md): result identity, declared inputs, grounded output contracts, protected storage, and invalidation.
2. [Structured facts](prd-metadata-enrichment-2-facts.md): deterministic extraction from OCR, QR values, and transcripts.
3. [Semantic insights](prd-metadata-enrichment-3-insights.md): suggested titles, summaries, categories, and topics through stable local model adapters.
4. [Integration and verification](prd-metadata-enrichment-4-integration.md): ordered execution, recovery, consent, deletion, and deployment checks.

Review each slice before beginning the next. This sequence covers the recommended first investment; it does not include every idea from the broader brainstorm.

## Product scope

- Suggested titles and concise summaries, stored separately from filenames and user-authored text.
- A small versioned category vocabulary and a bounded set of topics.
- Structured facts with evidence: URLs, email addresses, unambiguous dates, explicit currency amounts, and narrowly recognized error/reference codes. Product-name inference is a later extension after model quality is established.
- Image, audio, and video support through the metadata each already provides. Missing metadata reduces available insights; it never triggers a hidden media rescan.
- Existing local-AI consent, scanning policy, protected persistence, passive progress UI, and delete-all semantics apply to the entire feature.

Non-goals: editor analysis UI, Home search UI, automatic file renaming, automatic actions, cloud providers, embeddings/vector search, cross-capture grouping or comparisons, meeting tasks/decisions, chapters, and sensitive-content/sharing checks. No new user settings or per-model consent.

## Foundation contract

- Extend the existing analysis domain and store. Do not create a parallel database, queue, plugin framework, or general dependency graph.
- Every successful result has a durable, opaque result identity independent of its producing run. Replacing a result creates a new identity even when the text happens to match. Legacy results remain readable and receive repeatable identities without rewriting files on read.
- Derived outputs declare the exact first-level capabilities consulted and the result identity seen for each. Explicitly record absent optional inputs as well; a newly available input invalidates an output that previously ran without it. Successful empty input is different from absent input.
- Dependencies are limited to first-level file details, OCR, QR codes, descriptions, and transcripts for the same capture revision. Derived-on-derived processing and cross-capture dependencies are deferred.
- A derived result needs at least one present input. Its adapter/version and plan provenance remain available through the existing result envelope.
- Evidence points into a specific declared input and a specific text entry, using UTF-16 offsets and lengths. OCR regions, QR entries, transcript segments, and generated descriptions retain their existing bounds/times. Consumers can follow evidence back to that source; a model description remains an inference, not an observed fact.
- The first concrete derived payload is structured facts. Each observed fact carries its source text and one or more valid evidence spans. Slice 1 establishes the payload and validation; it does not extract facts or invoke a provider.
- Domain constructors validate immutable snapshots. Persistence validates dependencies and evidence before exposing results. Unknown schemas, invalid identities, ambiguous payloads, stale dependency references, or broken evidence fail closed.

## Refresh and deletion semantics

- Commit the replacement input and removal of its dependent results atomically in the same protected document. A reader cannot see a new OCR result alongside facts based on the replaced OCR result.
- An unrelated first-level update preserves derived outputs that did not consult it. Replacing a consulted input with an empty successful result still invalidates dependents.
- A same-source refresh may retain previous successful results until replacement succeeds, consistent with existing behavior. Failed/cancelled steps do not manufacture empty success or invalidate unchanged inputs. This does not certify the retained output as having been regenerated by the latest plan.
- Validate input identities again under the store publication gate. Reject late derived writes if any declared input changed, appeared, or disappeared.
- Existing generation/run/source fences still apply. Source changes clear all results. Delete removes basic and derived metadata together and rejects late writes. Interrupted physical cleanup keeps existing recovery semantics.

## Acceptance and validation

- Protected round trips preserve result identity, provenance, dependencies, fact values, and evidence; no metadata is stored in plaintext.
- Legacy documents remain readable with stable identities across repeated reads and reopening.
- Tests cover stale writes, unrelated updates, absent-to-present inputs, empty success, changed source, clear/restart, failed protection/publication, malformed documents, and out-of-range evidence.
- No provider packages, background execution, settings, progress behavior, or existing OCR reuse behavior change in this slice.
- Keep native-AOT-compatible, explicit source-generated serialization; no reflection-based polymorphic serialization.
